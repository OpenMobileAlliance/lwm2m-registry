   * ### SDF Final Review (Ari)
   * 

   * An SDF specification describes definitions of SDF Objects and their associated interactions (Events, Actions, Properties), as well as the Data types for the information exchanged in those interactions. Tools convert this format to database formats and other serializations as needed
   * [https://datatracker.ietf.org/doc/html/draft-ietf-asdf-sdf-16](https://datatracker.ietf.org/doc/html/draft-ietf-asdf-sdf-16)
   * 

   * Feedback: [https://github.com/ietf-wg-asdf/SDF/issues](https://github.com/ietf-wg-asdf/SDF/issues)
   * Status: WGLC ended, getting feedback before IESG submission.
   * MG: Why not convert xml to json directly?
   * AK: possible, reusing sdf tools simplifies.
   * 

   * AK: suggests JSON-SDF use. better support for range enumeration, min/max. If we chose JSON format then based it on JSON schema
   * MG: Are we dating (?) ourselves by creating this in IPSO? (xsd schema)
   * DN: ASDF could be used also for the NB API. As a way to abstract data models that would come from the device. Not explored atm. We do express all data models in a common SDF expression.
   * MG: is it a meta-data model?
   * DN: Common representation of the same info. Light control is the same regardless of IPSO, Zigbee, etc... common interface for all these devices.
   * MG: Obj 25 (GW)? 
   * DN: Diff beast. Protocol abstraction.
   * ...
   * DN, MG: everything is the same on the wire.
   * DN: exercise of whether you can express every LwM2M data model detail in SDF.
   * AK: SDF describes only what is on the data models. Not always common with other ecosystems. 
   * ...
   * MG: next steps?
   * AK: asks for feedback on the draft from OMA pov. Experience with IPSO models, DMSO objects need some attention. Any review is better than no review.
   * MG: feedback form?
   * AK: individual feedback on mailing list or github issues.
